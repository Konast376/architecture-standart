## 1. Функциональные требования (Use Cases)

| **№**| **Действующие лица или системы** | **Use Case** | **Описание** |
|---|-------------------------------|----------|-----------|
| **UC1** | Клиент (неавторизованный) → Сайт | Просмотр списка депозитов | Клиент видит на сайте список всех депозитов с общими (не персонализированными) ставками. Ставки загружаются из кэша (обновляются раз в несколько минут). |
| **UC2** | Клиент (неавторизованный) → Сайт | Подача заявки на депозит | Клиент заполняет ФИО и номер телефона, отправляет заявку. Система сохраняет заявку (статус «Новая») в БД депозитного шлюза. |
| **UC3** | Сайт → Депозитный шлюз | Передача заявки в кол‑центр | Шлюз передаёт заявку в систему кол‑центра через её API. Оператор кол‑центра видит заявку, звонит клиенту, при необходимости предлагает особые условия. |
| **UC4** | Клиент (авторизованный) → Интернет-банк | Просмотр персонализированных ставок | Клиент в ИБ видит список депозитов + ставки, рассчитанные индивидуально (на основе его кредитного риска, остатков на счетах). Шлюз вычисляет или получает ставки из АБС (через очередь, асинхронно). |
| **UC5** | Клиент (авторизованный) → Интернет-банк | Подача заявки на депозит | Клиент выбирает депозит, указывает счёт и сумму, подтверждает операцию СМС-кодом (через API СМС-шлюза). Заявка отправляется в шлюз со статусом «Ожидает подтверждения бэк-офиса». |
| **UC6** | Депозитный шлюз → Очередь сообщений | Постановка заявки в очередь для АБС | Шлюз кладёт заявку (с параметрами клиента, суммы, выбранной ставки) в очередь (например, RabbitMQ). Асинхронно, чтобы не нагружать АБС. |
| **UC7** | Бэк-офис (менеджер депозитов) → АБС | Обработка заявки | Менеджер через стандартный Delphi‑клиент АБС видит список новых заявок (шлюз записал их в специальную таблицу в Oracle). Менеджер проверяет условия, подтверждает или отклоняет заявку. Статус обновляется в АБС. |
| **UC8** | АБС → Шлюз (обратный вызов) | Уведомление о результате обработки | АБС через шлюз (или шлюз периодически опрашивает) получает статус заявки. При подтверждении шлюз инициирует СМС-уведомление «Депозит открыт». |
| **UC9** | Шлюз → СМС-шлюз (телеком-оператор) | Отправка СМС клиенту | Шлюз напрямую вызывает API СМС-шлюза для отправки кода подтверждения (UC5) и уведомлений (UC8). |

## 2. Нефункциональные требования (архитектурно значимые)

| **№** | **Требование** |
|---|-------------|
| **NFR1** | Доступность (24/7) для интернет-банка, сайта и депозитного шлюза. При отказе ЦОД должно происходить автоматическое переключение на резервный ЦОД. |
| **NFR2** | **Избегать прямых синхронных вызовов к АБС** – все операции записи (создание/обновление заявок) идут через очереди сообщений. |
| **NFR3** | Время отклика интерфейса (просмотр списка депозитов, отправка заявки) – не более 200 мс (миллисекунды). |
| **NFR4** | Нагрузка на АБС не должна увеличиться более чем на 5% по сравнению с текущей. Все запросы на чтение ставок и справочников должны обслуживаться из кэша. |
| **NFR5** | Горизонтальное масштабирование интернет-банка и депозитного шлюза – возможность добавлять узлы без остановки сервиса. |
| **NFR6** | Шифрование всех взаимодействий между системами (TLS 1.2+). Для межсервисного общения внутри банка – mTLS. |
| **NFR7** | Все изменения должны вноситься силами команды банка, без доработок ядра интернет-банка и системы кол-центра подрядчиком. Использовать Java (Spring Boot) для новых компонентов (экспертиза есть). |
| **NFR8** | Логирование каждого действия с заявкой (кто, когда, статус) в централизованном хранилище с retention 3 года (аудит). |

## 3. Решение

## Контекст (Context)
Банк «Стандарт» планирует запустить онлайн‑открытие депозитов и накопительных счетов в интернет-банке и на сайте.
- Текущий интернет-банк — монолит ASP.NET MVC 4.5, интегрированный с АБС напрямую через БД.
- АБС (Oracle + Delphi) перегружена, масштабируется только вертикально.
- Ставки по депозитам рассчитываются вручную в Excel, хранятся вне АБС.
- Бизнес требует высокую доступность (99,9%), производительность (миллисекундные отклики) и возможность развития силами банка.

## Причина (Facing)
- Прямые синхронные вызовы из интернет-банка к АБС создают риск отказа АБС при росте онлайн-заявок.
- Ядро интернет-банка нельзя дорабатывать (требует привлечения подрядчика, несовместимо с горизонтальным масштабированием).
- Текущие справочники загружаются более секунды — нужно ускорить.
- Отсутствует единый источник ставок и механизм их кэширования.
- Система не готова к высоким нагрузкам и отказоустойчивости (один ЦОД, один сервер).

## Принято (We decided for)
**Принять комплекс архитектурных решений, образующих «Систему открытия депозитов» как отдельный слой между фронтами и АБС:**

1. **Асинхронная связь с АБС через очередь сообщений**
    - Внедрить RabbitMQ (совместим с .NET и Java).
    - Интернет-банк и сайт отправляют заявки в очередь `deposit_requests`.
    - Депозитный шлюз (см. п.2) читает очередь и асинхронно пишет заявки в промежуточные таблицы Oracle.
    - Результат обработки заявки (подтверждение/отказ) АБС выставляет в таблицу `deposit_results`, шлюз опрашивает и отправляет уведомления.

2. **Создание отдельного депозитного шлюза (микросервиса)**
    - Разработать на **Java Spring Boot** (экспертиза в банке есть).
    - База данных шлюза — **PostgreSQL** (унификация с системой кол-центра).
    - Шлюз предоставляет REST API для интернет-банка и сайта.
    - Масштабируется горизонтально, не зависит от ядра интернет-банка.

3. **Кэширование ставок и справочников**
    - Использовать **Redis**.
    - Общие ставки кэшировать на **5 минут**, персонализированные — на **1 час** (или до изменения профиля клиента).
    - При промахе кэша шлюз асинхронно запрашивает ставки из АБС через очередь с высоким приоритетом.

4. **Отказоустойчивая архитектура с горизонтальным масштабированием**
    - Интернет-банк: минимум 2 экземпляра + балансировщик Nginx. Сессии вынести в Redis.
    - Депозитный шлюз: 2+ реплики + балансировщик.
    - RabbitMQ кластеризовать с зеркалированием очередей.
    - Базы данных: репликация PostgreSQL (master‑standby), MS SQL — Always On.
    - *Для MVP допустимо упрощение:* два сервера ИБ в одном ЦОД с Redis и ручным переключением резервного ЦОД.

**Аргументация:**
- Ни одно из решений не требует изменения ядра интернет-банка (подрядчик не нужен).
- Используются технологии, где у банка есть экспертиза (.NET, Java, Oracle, MS SQL).
- Асинхронность и кэширование гарантируют защиту АБС от перегрузки.
- Горизонтальное масштабирование закладывает основу для роста нагрузки.

## Отклонено (Neglected)

| Альтернатива | Причина отклонения |
|--------------|---------------------|
| Прямая синхронная запись заявок в АБС (как для платежей) | Высокий риск отказа АБС, не соответствует требованию доступности 99,9%. |
| Доработка монолита интернет-банка для добавления депозитного функционала | Требует привлечения подрядчика, не решает проблему масштабирования. |
| Использование Kafka вместо RabbitMQ | Несовместима с текущей платформой ИБ (.NET 4.5), нет экспертизы. |
| Хранение ставок только в АБС без кэширования | Приведёт к росту нагрузки на Oracle и невозможности миллисекундного отклика. |
| Оставить ИБ в одном ЦОД без балансировки | Не даст достичь 99,9% доступности и горизонтального масштабирования. |

## Чтобы достичь (To achieve)
- Клиент видит список депозитов и ставки с откликом < 200 мс (благодаря кэшу).
- Заявка на депозит принимается мгновенно («Заявка принята»), фактическая обработка в АБС — асинхронно.
- АБС не испытывает дополнительной нагрузки (все операции записи идут через очередь, чтение — через кэш).
- Система выдерживает рост числа онлайн-заявок без отказа (горизонтальное масштабирование).
- Разработка и поддержка ведутся силами банка (без доработок ядра ИБ).

## Принимая что (Accepting that)
- Появляются новые компоненты (депозитный шлюз, RabbitMQ, Redis), усложняющие инфраструктуру и требующие мониторинга.
- Задержка между подачей заявки и её отображением в АБС составляет 1–5 секунд (приемлемо для MVP).
- Кэширование может привести к показу устаревших ставок максимум на 5 минут (компромисс между актуальностью и производительностью).
- Полноценная отказоустойчивость (автоматическое переключение ЦОД) будет реализована после MVP, на первом этапе — только ручное переключение.
- Требуется обучение команды эксплуатации работе с RabbitMQ, Redis и новыми компонентами.
